# GPU-FPGA异构ViT推理建模周报

## 一、本周研究目标

本周围绕Jetson GPU/CPU与PCIe FPGA协同执行ViT推理开展无硬件阶段建模。研究重点不是实现单bit量化或FPGA Linear内核，而是构建异构运行与通信模型，分析FPGA计算收益能否覆盖GPU与FPGA之间的数据传输开销，并为后续真实硬件实验准备可校准的运行框架。

核心问题可以表述为：

> 当ViT的部分Linear层放到FPGA执行时，怎样综合考虑GPU计算、FPGA计算、片间通信、设备排队和并发流水线，使端到端效果优于GPU-only？

## 二、本周完成工作

### 1. 建立SimGrid异构模拟环境

在WSL2 Ubuntu 24.04环境中安装并跑通SimGrid 3.35，依次验证了虚拟设备计算、GPU-FPGA传输、GPU-only与FPGA卸载比较、共享资源竞争等基础机制。

### 2. 确认ViT工作负载

对当前`vit.onnx`进行结构检查。模型并不是ViT-Small，而是ViT-Base/16-like：

- 输入：`[1, 3, 224, 224]`
- 输出：`[1, 1000]`
- 隐藏维度：768
- Transformer Block：12个
- 参数量：约8645万
- 可作为GPU/FPGA候选的Linear：49个

模型被转换为125个粗粒度调度任务和148条依赖边，残差连接等依赖均被保留。

### 3. 提取真实激活数据量

在batch=1、FP32激活、FPGA权重预加载的假设下，单个Transformer Block中各类Linear独立卸载的输入输出总数据量为：

| Linear类型 | 单次往返逻辑数据量 |
| --- | ---: |
| QKV | 2.421 MB |
| Attention Projection | 1.210 MB |
| FFN1 | 3.026 MB |
| FFN2 | 3.026 MB |

若49个Linear全部放到FPGA，一个请求共产生约116.198 MB跨设备逻辑数据。普通主机中转需要在两条链路各传输一次，对应约232.397 MB物理链路流量。

### 4. 审计IRIS异构运行时

检查了IRIS 3.0.0源码。IRIS支持CUDA GPU、OpenCL/Xilinx FPGA、任务DAG、数据管理、异步设施和自定义调度策略，因此适合作为后续真实硬件运行时基线，但它不是性能模拟器。

源码审计发现：

- CUDA GPU与OpenCL FPGA属于不同设备类型，通用数据路径通常不能直接使用CUDA D2D。
- 不支持直接传输时，IRIS会采用`GPU -> HOST -> FPGA`及反向主机中转。
- `iris_profile`虽然记录了传输历史，但选择设备时主要比较平均内核时间，没有把输入输出通信时间完整加入决策。
- 这会导致“FPGA内核更快，但端到端推理更慢”的错误卸载。

因此，当前方案采用SimGrid负责模拟，IRIS负责未来真机部署，并计划将通信感知策略移植为IRIS自定义策略。

### 5. 完整ViT DAG基线实验

实现并比较了以下策略：

1. GPU-only。
2. 所有Linear静态放到FPGA。
3. IRIS-profile-like，只比较内核计算时间。
4. IRIS-data-like，优先选择数据所在设备。
5. Communication-aware EFT，同时考虑输入传输、计算、已知GPU后继的返回传输和资源排队。

在参考主机中转条件下，GPU-only为22.184 ms，全部Linear卸载为48.870 ms，IRIS计算时间策略为48.841 ms。通信感知策略识别出卸载不划算，选择0个FPGA Linear并保持22.184 ms。

调试过程中还发现，普通EFT若只计算输入传输，会错误选择QKV和FFN1，因为它把FPGA输出返回GPU的开销推迟给了后继任务。加入一跳输出前视后，该问题得到修正。

## 三、最终综合设计空间实验

### 1. 实验范围

综合实验扫描了：

- 通信路径：主机中转两次拷贝、共享映射一次拷贝、直接DMA一次拷贝。
- 有效带宽：2、4、8、16 GB/s。
- 单向固定延迟：5、10、20、50 us。
- FPGA Linear相对GPU计算加速比：2、4、8、16倍。
- 调度策略：GPU-only、全部卸载、通信感知选择性卸载。

共得到192组硬件条件、576条策略扫描结果。随后选择4个代表场景，在SimGrid中分别回放1、2、4、8个同时到达的推理请求，共得到48组并发实验结果。

所有结果均标记为`sensitivity`，不能作为目标硬件性能预测。

### 2. 不同通信路径的可盈利范围

| 通信路径 | 通信感知策略可盈利条件 | 全部卸载可盈利条件 | 最大条件性加速比 |
| --- | ---: | ---: | ---: |
| 主机中转两次拷贝 | 6/64 | 4/64 | 1.105倍 |
| 共享映射一次拷贝 | 19/64 | 15/64 | 1.541倍 |
| 直接DMA一次拷贝 | 19/64 | 15/64 | 1.541倍 |

对于主机中转路径，在当前测试范围内：

- 低于16 GB/s时没有出现可盈利条件。
- 带宽达到16 GB/s后，仍需要FPGA Linear至少约8倍计算加速。
- 单向固定延迟需要不高于20 us。
- 固定延迟为50 us时，即使FPGA计算加速达到16倍，也没有超过GPU-only。

一次拷贝路径明显扩大了异构执行的可盈利区域。最佳测试条件为16 GB/s、5 us和16倍FPGA Linear加速，通信感知策略选择48个Linear，解析结果相对GPU-only达到条件性1.541倍加速。

共享映射和直接DMA在输入相同有效带宽、固定延迟时得到相同结果。这只表示当前抽象成本相同，不代表两种真实机制性能相同；缓存一致性、内存映射和驱动开销需要真机测量。

### 3. 单请求延迟与多请求吞吐率

| 场景与策略 | 单请求效果 | 8请求吞吐效果 | FPGA Linear数 |
| --- | ---: | ---: | ---: |
| 参考主机中转，全部卸载 | 0.454倍 | 0.723倍 | 49 |
| 参考主机中转，通信感知 | 1.000倍 | 1.000倍 | 0 |
| 有利主机中转，全部卸载 | 0.990倍 | 2.701倍 | 49 |
| 有利主机中转，通信感知 | 1.026倍 | 2.882倍 | 36 |
| 一次拷贝中等条件，全部卸载 | 0.851倍 | 1.435倍 | 49 |
| 一次拷贝中等条件，通信感知 | 1.000倍 | 1.000倍 | 0 |

有利主机中转条件下，通信感知策略选择12个QKV、12个FFN1和12个FFN2，共36个FPGA Linear。8个请求在61.577 ms内完成，吞吐率为129.918 requests/s；GPU-only吞吐率为45.077 requests/s，对应条件性2.882倍吞吐提升。

实验还发现，某些条件下全部卸载会使单请求延迟变差，但多请求吞吐率提高。这是因为多个请求之间可以形成GPU计算、PCIe传输和FPGA计算流水线。因此，后续运行时必须区分两种目标：

- 低延迟模式：优先保证单次请求完成时间，不进行不盈利卸载。
- 高吞吐模式：允许单请求延迟略有增加，通过跨请求流水线提高单位时间处理量。

不能把高吞吐模式的收益描述成单次推理加速。

## 四、本周结论

1. FPGA内核计算快并不等于异构推理快，输入输出通信必须加入调度决策。
2. 在当前ViT图中，大多数Linear前后都是GPU算子，单请求内部很难隐藏通信，因此选择性卸载比全部卸载更合理。
3. 主机中转的两次数据移动显著压缩可盈利区域，减少一次数据拷贝比单纯提高FPGA内核速度更有系统价值。
4. 固定通信延迟非常关键。大量Linear分别卸载时，每层都会支付固定开销，50 us级固定延迟在测试范围内已足以抵消FPGA收益。
5. 跨请求流水线可以显著提高吞吐率，但需要与单请求低延迟目标分开建模和评价。
6. IRIS当前计算历史策略存在忽略端到端通信的空间，可以把通信感知选择和延迟/吞吐双模式调度作为后续候选研究方向。

## 六、当前局限

目前没有Jetson和FPGA真实硬件，因此以下数据仍是条件性假设：

- GPU各类算子的实际执行时间。
- FPGA四类Linear及classifier的实际内核时间。
- FPGA调度和启动开销。
- Jetson共享内存、pinned memory和PCIe DMA的真实路径。
- 不同传输大小下的固定延迟和有效带宽。
- 数据布局转换、缓存同步、功耗和温度降频。

因此目前可以证明模拟方法和调度逻辑成立，也可以给出硬件需要达到的条件，但不能声称真实系统已经获得1.541倍延迟加速或2.882倍吞吐提升。

## 七、后续真机阶段计划

硬件到位后不重新设计模拟器，而是直接校准现有接口：

1. 使用TensorRT或CUDA事件测量GPU上125个粗粒度任务，至少记录均值、P50和P95。
2. 测量FPGA上QKV、Projection、FFN1、FFN2和classifier内核时间。
3. 对不同数据大小分别测试GPU/共享内存、HOST/FPGA PCIe、pinned/mapped memory及可用的直接DMA路径。
4. 测量单向固定延迟、有效带宽、双向竞争和计算通信重叠能力。
5. 将实测数据填入现有`task_costs.csv`和`platform_profile.json`。
6. 保持DAG和策略不变，重新运行模拟并与真机结果比较，计算预测误差。
7. 将通信感知策略实现为IRIS自定义策略，对比GPU-only、全部卸载、IRIS原策略和改进策略。

无硬件阶段到此完成并冻结。继续增加假设参数不会提高结论可信度，下一步有效证据必须来自目标板卡测量。
